# XianWen v1 技术方案

- 状态：Draft
- 更新时间：2026-10-22
- 关联文档：`docs/prd-v1.md`、`docs/term_explanation.md`
- 适用范围：XianWen MVP 的工程实现、插件开发、测试与公开部署

## 1. 文档目的

本文档固化当前讨论确定的技术方向，作为后续工程初始化、插件规范、CI/CD 和验收实现的共同依据。

本文档不替代产品 PRD。产品范围、回合规则、AI 使用限制和插件验收要求以 `docs/prd-v1.md` 为准。

## 2. 技术目标

MVP 需要在较短时间内交付一个公开可访问、可完整游玩、可扩展插件的浏览器文字游戏，同时满足以下约束：

1. 游戏规则由确定性的 Python 代码执行，AI 只生成展示文本。
2. 用户 API Key 只存在于当前页面内存，经服务端即时转发，不持久化。
3. 玩家存档可保存在浏览器本地，并为未来迁移数据库保留接口。
4. 插件以独立包提供，使用审核后随站点发布的声明式内容和受限 Python 规则。
5. 无账号、无数据库、无服务端会话、无自由文字输入。
6. 测试、Lint、类型检查均可在本地和 CI 中使用统一命令执行。

## 3. 核心技术选型

| 领域 | 选型 | 说明 |
| --- | --- | --- |
| 语言 | Python 3.12+ | 游戏核心、Web 服务和插件均使用 Python |
| Web 框架 | FastAPI | 提供页面路由、回合接口和模型代理 |
| 模板 | Jinja2 | 服务端渲染页面和 HTMX 片段 |
| 局部交互 | HTMX | 提交表单并替换场景、选项和结算区域 |
| 客户端状态 | Alpine.js | 临时 API Key、本地存档和少量交互 |
| 校验 | Pydantic | 请求、响应、存档、插件和 AI 输出校验 |
| HTTP 客户端 | httpx | 异步调用模型服务 |
| 工程管理 | uv | 管理 Python 版本、虚拟环境和依赖 |
| 依赖配置 | `pyproject.toml` + `uv.lock` | 声明依赖并锁定可复现版本 |
| 测试 | pytest | 核心规则、插件、API 和迁移测试 |
| Lint / 格式 | ruff | 静态检查与格式检查 |
| 类型检查 | mypy | Python 静态类型检查 |
| 部署 | Docker + 单个 FastAPI 服务 | 页面、静态资源和模型代理同源部署 |
| CI/CD | GitHub Actions | CI 检查，主分支通过后触发部署 |
| 存档 | 浏览器 `localStorage` | 通过可替换仓储层封装，当前不引入数据库 |

## 4. 总体架构

```text
┌────────────────────────────────────────────┐
│ 浏览器                                     │
│ Jinja2 页面 + HTMX + Alpine.js             │
│ localStorage：游戏存档                     │
│ 页面内存：用户 API Key                     │
└───────────────────┬────────────────────────┘
                    │ HTTPS，同源请求
                    ▼
┌────────────────────────────────────────────┐
│ 单个 FastAPI / Docker 服务                 │
│                                            │
│ web         页面路由与 HTMX 片段           │
│ core        回合、规则、状态与结局         │
│ plugins     插件加载、校验与错误隔离       │
│ ai          服务商适配、校验与后备模式     │
│ persistence 存档接口与版本迁移             │
└───────────────────┬────────────────────────┘
                    │ HTTPS
                    ▼
┌────────────────────────────────────────────┐
│ DeepSeek / 千问 / 智谱 GLM                 │
└────────────────────────────────────────────┘
```

MVP 不包含数据库和服务端 Session。除当前请求所需的临时数据外，服务端不保存玩家的游戏状态和 API Key。

## 5. 分层与依赖方向

### 5.1 Web 层

负责：

- 渲染开始页、游戏页和结局页。
- 接收 HTMX 请求并返回 HTML 片段。
- 读取并转发临时 API Key。
- 生成和接收玩家存档。
- 展示校验后的 AI 文本或后备文本。

不得负责：

- 筛选种子事件。
- 应用数值效果。
- 决定死亡、突破或结局。
- 直接调用模型服务。

### 5.2 游戏核心层

负责：

- 游戏状态模型与状态迁移。
- 候选种子筛选。
- 世界线排期和推进保证。
- 选项效果应用。
- 死亡、突破、结局判定。
- 生成 AI 可见的受限上下文。

游戏核心不得依赖 FastAPI、Jinja2、HTMX、浏览器存储或模型 SDK。核心函数应优先保持纯函数，随机性必须来自可注入的随机源。

### 5.3 插件层

负责：

- 扫描并读取独立插件包。
- 校验插件清单、内容、规则和版本。
- 将合法内容注册到统一内容库。
- 隔离单个插件的加载和运行错误。
- 管理插件命名空间和私有状态。

插件层不能绕过核心直接修改状态。插件返回标准效果，由核心校验并应用。

### 5.4 AI 层

负责：

- 服务商配置与模型白名单。
- 用户 Key 的即时转发。
- 构造模型请求并解析结构化输出。
- 校验 AI 是否只修改允许扩写的字段。
- 处理超时、重试、预算和后备模式。
- 对日志和错误信息中的敏感内容进行脱敏。

AI 层不得决定游戏规则后果。

### 5.5 持久化层

负责：

- 定义存档读写接口。
- 当前使用浏览器本地存储实现。
- 校验存档版本并执行迁移。
- 为未来的数据库存档实现保留替换点。

## 7. 状态与回合数据流

### 7.1 状态归属

- **已提交游戏状态**：由浏览器持有，可写入 `localStorage`。
- **当前待选回合上下文**：可以保存在页面内存中，刷新后允许重新生成。
- **用户 API Key**：只存在 Alpine.js 内存，不进入游戏状态或存档。
- **服务端**：只处理当前请求，不保存会话状态。

### 7.2 开始回合

1. 浏览器从本地存档恢复已提交状态，或创建新游戏状态。
2. 浏览器提交状态、模型服务、模型和临时 Key。
3. FastAPI 校验状态与模型白名单。
4. 核心筛选 2-3 个候选种子事件。
5. AI 层在可用时调用模型扩写场景和选项文本。
6. 服务端校验 AI 响应；失败时重试一次，仍失败则使用种子后备文本。
7. 浏览器接收场景、选项和当前回合上下文，Key 不写入页面持久存储。

### 7.3 处理选择

1. 浏览器提交已提交状态、当前回合上下文、种子 ID 和选项 ID。
2. FastAPI 校验该种子和选项确实属于当前回合。
3. 核心应用标准效果并判定世界线推进、死亡、突破或结局。
4. 服务端返回结算片段和新的可序列化游戏状态。
5. 浏览器替换页面片段，并将新状态写入 `localStorage`。

玩家选择后不需要再次提交 API Key。

### 7.4 客户端篡改边界

单机游戏允许玩家在理论上修改浏览器存档。服务端仍需校验结构和回合合法性，但不能依赖客户端状态作为可信安全边界。

客户端篡改只能影响玩家自己的单机体验，不属于 MVP 的安全防护目标。

## 8. 存档设计

存档使用带版本号的 JSON，概念结构如下：

```json
{
  "schema_version": 1,
  "save_id": "generated-id",
  "game": {},
  "plugin_state": {},
  "plugin_versions": {},
  "usage": {}
}
```

约束：

- `schema_version` 必须存在。
- 用户 API Key 绝不进入存档。
- 插件状态必须按插件 ID 隔离。
- 存档加载前必须经过 Pydantic 校验。
- 存档升级通过明确的迁移函数执行，不静默丢弃未知字段。
- 每回合结算后自动保存。
- 当前只保留一个当前局和已完成人物志。
- 浏览器端通过 `SaveRepository` 抽象读写，不把 `localStorage` 调用散落在 UI 中。

未来可以增加数据库实现，但不得要求重写游戏核心。

## 9. 游戏核心规则

- 每回合代表一年，共 20 回合。
- 每回合先筛选候选种子，再由 AI 选择并扩写其中一个。
- AI 只能从候选中选择，不得检索或修改整个种子库。
- 选项数量固定为 2-4 个，ID 和规则后果来自种子。
- 每个事件至少有一个带代价的退路。
- 所有数值、状态、死亡、突破和结局由核心判定。
- 世界线排期由规则保证，AI 不决定世界线推进。
- 被忽略的世界线仍继续推进，并至少每四年产生一次可见变化。
- 第 5、10、15、20 年必须有灵潮重大事件；中间年份通过时局摘要补齐可见变化。

## 10. AI 服务边界

### 10.1 服务预设

服务端只允许以下预设：

- DeepSeek
- 千问
- 智谱 GLM

每个预设由服务端配置：

- 真实接口地址。
- 默认模型。
- 经过测试的有限模型列表。
- 请求和响应适配方式。

客户端不能提交任意接口地址或自由文本模型名。具体模型和接口需通过实际测试后锁定。

### 10.2 Key 安全

- Key 只保存在当前页面内存中。
- Key 不写入 `localStorage`、存档、URL、日志或分析数据。
- Key 经同一个 FastAPI 服务即时转发给模型服务。
- 服务端不得记录完整请求头、请求体和上游凭据。
- 错误信息不得回显完整 Key。
- 刷新或关闭页面后必须重新输入 Key。
- 允许重新输入 Key，但不允许同一局中途更换服务或模型。

### 10.3 输出校验

AI 响应至少校验：

- 选中的种子 ID 属于当前候选列表。
- 返回的选项 ID 与种子完全一致。
- 每个选项都有对应结果文本。
- 未包含任何状态修改指令。
- 未新增永久地点、人物、物品或结局条件。

校验失败时重试一次；再次失败则使用种子后备文本。

### 10.4 调用与预算

- 每回合最多一次常规模型调用。
- 终局允许额外一次人物志总结调用。
- 每局最多 25 次模型调用，包含重试和终局调用。
- 默认 token 预算为 60k。
- 达到 80% 时提示用户。
- 达到 100%、无 Key、网络失败或服务错误时自动进入后备模式。

## 11. 插件系统

### 11.1 信任模型

MVP 采用审核后随站点发布的可信插件模型：

- 公开访客不能上传或即时执行插件代码。
- 插件通过代码审核后与站点一起部署。
- 不承诺对恶意 Python 代码提供沙箱隔离。
- 不向插件提供用户 API Key 或其他秘密。
- 单个插件出错时只禁用该插件，主游戏继续运行。

### 11.2 插件包结构

目标包结构：

```text
plugins/<plugin-id>/
├── plugin.toml
├── content/
│   ├── locations.toml
│   ├── events.toml
│   └── endings.toml
└── rules.py
```

`rules.py` 可选。纯数据插件不需要编写 Python。

### 11.3 清单

MVP 清单至少包含：

- `id`：稳定且唯一的插件 ID。
- `name`：显示名称。
- `version`：插件版本。
- `api_version`：插件接口版本。
- 可选的游戏兼容范围。

### 11.4 声明式内容

地点、事件、人物、物品和结局优先使用 TOML/JSON 声明。

每个事件至少包含：

- 唯一 ID。
- 所属插件命名空间。
- 地点、阶段、条件和权重。
- 基础场景后备文本。
- 2-4 个固定选项。
- 每个选项的标准效果。
- 每个选项的基础结果后备文本。

所有事件和结果缺少后备文本时，插件校验不通过。

### 11.5 规则钩子

复杂条件或特殊规则可以使用经过审核的 Python 函数。

约束：

- 输入上下文只读。
- 规则函数必须确定；随机性来自宿主提供的随机源。
- 不得直接修改核心状态。
- 不得访问网络、用户 Key 或其他插件状态。
- 返回结果必须符合宿主定义的条件或效果格式。
- 异常或非法返回值会导致该插件被禁用。

### 11.6 标准效果

插件不直接修改状态，只返回标准效果。MVP 效果类型至少覆盖：

- 数值变化。
- 声望变化。
- 设置或清除标记。
- 增加或移除物品。
- 切换地点。
- 写入插件命名空间内的私有状态。

死亡、突破和最终结局仍由核心规则判定。

### 11.7 插件状态与版本

- 插件私有状态必须是 JSON 可序列化数据。
- 每个插件只能访问自己的状态命名空间。
- 存档记录启用插件的 ID 和版本。
- 插件不兼容时禁止启用并显示原因。
- 插件被禁用后，其历史状态保留在存档中，避免再次启用时丢失。
- 插件状态格式升级由插件声明的迁移能力处理。

### 11.8 加载与故障隔离

加载流程：

1. 扫描插件目录。
2. 读取并校验 `plugin.toml`。
3. 读取并校验声明式内容。
4. 加载可选的规则模块。
5. 校验 ID 唯一性和版本兼容性。
6. 注册到内容库并冻结注册表。

运行期规则异常时，宿主应停止使用该插件并重新选择核心事件。插件不得影响其他插件的加载和运行。

### 11.9 未来扩展

未来可以增加：

- 完整 Python 插件入口和生命周期钩子。
- 自定义行动和插件依赖声明。
- 插件存档迁移函数。
- 受限界面扩展点。

扩展必须通过新的 `api_version` 演进，不能直接暴露核心 `GameState` 供插件随意修改。

## 12. Web 页面与交互

- 使用 Jinja2 渲染固定页面外壳。
- 使用 HTMX 替换场景、选项、结算和属性面板。
- 使用 Alpine.js 管理临时 Key、本地存档和少量页面状态。
- HTMX 和 Alpine.js 静态文件随项目发布，不依赖 CDN。
- 页面必须支持桌面浏览器，并保证手机端可阅读和选择。
- 插件只能扩展内容与规则，不能修改主界面外壳。
- Jinja2 默认转义 AI 和插件文本，禁止直接渲染未经校验的 HTML。

## 13. 部署

采用单个 Docker 化 FastAPI 服务：

- 同一服务提供页面、静态资源和模型代理。
- 生产环境使用一个公开域名。
- 不单独部署前端或数据库。
- 平台可以后续选择，但应支持 Docker 或等价 Python 运行环境。
- 部署后必须实际验证一次完整 20 回合流程，而不只是检查首页。

低成本平台若存在休眠或冷启动，需在最终演示前完成实测。

## 14. CI/CD

### 14.1 CI

GitHub Actions 在 Pull Request 和分支推送时运行：

```text
uv sync --frozen
uv run ruff check .
uv run ruff format --check .
uv run mypy src
uv run pytest
docker build .
```

要求：

- 测试不得调用真实模型服务。
- AI 相关测试使用 mock 或固定响应。
- 至少覆盖一次无 Key 的后备模式流程。
- 所有检查退出码必须为 0。
- Docker 构建失败视为 CI 失败。

### 14.2 CD

- 仅当主分支通过 CI 后才允许部署。
- 部署凭证存放在 GitHub Secrets。
- 建议使用 `DEPLOY_WEBHOOK` 触发部署平台，避免在仓库中保存平台令牌。
- 部署后增加一次公开 URL 健康检查。
- 用户 API Key 与 CI/CD Secrets 完全分离。

### 14.3 分支保护

- 主分支禁止直接推送。
- Pull Request 必须通过 CI 检查。
- 至少一名组员审核。
- CI 未通过时禁止合并。
- 工作流中的默认分支名称必须与 GitHub 实际默认分支一致。

## 15. 测试与质量门禁

### 15.1 测试范围

- 核心状态迁移和效果应用。
- 候选事件筛选与世界线保障。
- 死亡、突破和结局判定。
- 存档序列化、反序列化和版本迁移。
- 插件清单、内容、ID、后备文本和版本校验。
- 插件异常隔离与禁用。
- AI 响应结构校验、重试和后备切换。
- API 请求校验和 Key 脱敏。
- 无 AI 的固定后备模式完整流程。
- Docker 镜像构建与启动冒烟测试。

### 15.2 质量命令

工程初始化后，以下命令必须在本地和 CI 中保持一致：

```powershell
uv run ruff check .
uv run ruff format --check .
uv run mypy src
uv run pytest
```

完成定义：以上命令和 Docker 构建退出码均为 0。

当前仓库尚无 Python 工程、`pyproject.toml` 或测试，因此这些命令还不可执行。

## 16. 安全约束

- 禁止提交 `.env`、真实模型 Key 或平台凭证。
- 用户 Key 只在页面内存和单次服务端请求中存在。
- 服务端仅允许预设服务和白名单模型。
- 日志不得记录 Key、完整请求体或敏感请求头。
- Jinja2 必须保留自动转义。
- 所有外部输入必须经过 Pydantic 校验。
- 设置请求体大小和上游请求超时。
- 插件审核是 MVP 的安全边界，不宣称恶意代码隔离。
- 模型输出永远不能直接修改游戏状态。

## 17. 未来演进

### 17.1 数据库

当前使用浏览器存档。未来通过 `SaveRepository` 增加数据库实现，可支持云存档、跨设备同步或账号。

数据库不是横向扩容的前置条件；当前无状态服务本身已便于增加实例。

### 17.2 完整 Python 插件包

当前插件是完整插件包模型的子集。未来通过版本化 API 增加生命周期钩子、自定义行动、迁移函数和受限扩展点。

必须保持：

- 插件提交效果，核心应用效果。
- 插件不能直接决定死亡、突破和最终结局。
- 插件不能访问用户 Key。
- 旧版插件在兼容范围内继续运行。

## 19. 验收映射

技术方案至少支撑以下验收：

- 无 Key 时可完成完整游戏。
- AI 非法输出会被拒绝并回退。
- 用户 Key 不进入存档、日志或仓库。
- 插件可独立增加地点、事件、条件和结局变化。
- 插件出错时只禁用该插件。
- 插件存档可保存并恢复。
- 本地不存在数据库依赖。
- GitHub Actions 可阻止失败代码合并。
- Docker 公开部署可访问并完成试玩。
