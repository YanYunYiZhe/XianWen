# 插件系统

## 一、契约是什么

**契约（Contract）就是双方事先约定好的合作规则。**

最直观的类比是 USB 接口：

- 电脑承诺提供固定的接口形状、供电和数据协议。
- U 盘承诺按同样的协议通信。
- 双方都不需要知道对方内部怎么实现。
- 如果 U 盘不符合协议，电脑可以拒绝连接，而不是让电脑死机。

插件契约也是同样意思：

> 游戏承诺：我会用固定方式加载你、调用你，并处理你返回的结果。
> 插件承诺：我只使用规定格式，只返回允许的内容，不越界修改游戏。

所以契约不只是“有几个函数”，它还包括：

- 数据格式。
- 谁负责修改状态。
- 出错时怎么办。
- 哪些事情禁止做。
- 版本不兼容时怎么处理。
- 存档如何保存和恢复。

## 二、API 和契约的区别

这两个词容易混。

### API

API 是游戏提供给插件的“可调用功能清单”。

例如：

```
游戏提供：
- 注册新地点
- 注册新事件
- 注册新结局
- 注册条件函数
- 读取当前状态摘要
```

### 契约

契约是更完整的约定，包括：

- API 怎么调用。
- 参数是什么类型。
- 返回值必须是什么格式。
- 函数能不能修改状态。
- 函数报错后游戏怎么处理。
- 插件版本和游戏版本如何兼容。
- 哪些数据可以写入存档。

可以理解为：

> **API 是工具清单，契约是使用说明书和双方责任。**

## 三、插件在游戏里是什么

插件不是游戏本身，而是一个独立扩展包。

游戏启动时，会去固定目录寻找插件：

```
plugins/
  example-mining/
  example-herbalism/
```

每个目录都是一个插件包。

游戏会做这些事：

1. 读取插件身份信息。
2. 检查插件版本是否兼容。
3. 读取新增地点、事件、结局。
4. 检查文本、选项和效果是否合法。
5. 如果有自定义规则，就加载对应 Python 函数。
6. 把合法内容加入游戏内容库。
7. 如果某个插件加载失败，只禁用该插件。

简化流程：

```
扫描插件目录
    ↓
读取 plugin.toml
    ↓
校验插件清单
    ↓
加载内容数据
    ↓
加载可选 Python 规则
    ↓
加入游戏内容库
```

插件代码在 FastAPI 服务端运行，不会发送给浏览器。玩家只看到插件内容最终生成的网页。

## 四、插件的基本组成

一个插件包通常包含以下部分。

### 1. 清单

清单描述插件是谁：

```
id = "mining_echoes"
name = "矿道回声"
version = "0.1.0"
api_version = "1"
```

- `id`：插件唯一标识，不能和别的插件重复。
- `version`：插件自己的版本。
- `api_version`：插件使用的接口契约版本。
- `name`：玩家看到的名称。

### 2. 内容数据

例如一个新地点：

```
[[locations]]
id = "mining_echoes.locations.abandoned_shaft"
name = "废弃矿道"
description = "矿灯早已熄灭，风从坍塌的坑道深处吹出来。"
```

新增事件：

```
[[events]]
id = "mining_echoes.events.collapsed_tunnel"
location = "mining_echoes.locations.abandoned_shaft"
fallback_text = "你听见矿道深处传来敲击声，像是还有人被埋在下面。"

[[events.choices]]
id = "rescue"
text = "冒险救人"
effects = [
  { type = "injury_delta", value = 1 },
  { type = "reputation_delta", faction = "scatter", value = 2 }
]
fallback_result = "你把矿工拖了出来，自己也被落石擦伤。"

[[events.choices]]
id = "leave"
text = "记下位置，暂时离开"
effects = [
  { type = "flag_set", key = "mining_echoes.knows_collapse", value = true }
]
fallback_result = "你没有贸然进去，只把入口位置记了下来。"
```

这里插件没有直接写：

```
player.injury += 1
```

它只声明：

```
这个选项应该产生“伤势增加 1”的效果
```

真正修改玩家状态的是游戏核心。

### 3. 后备文本

`fallback_text` 和 `fallback_result` 是必须的。

因为 AI 可能失败：

- 没有 API Key。
- 网络断开。
- 模型响应格式错误。
- Token 用完。

这时游戏直接使用插件作者写好的文本，仍然可以继续玩。

### 4. 可选规则代码

如果数据配置无法表达复杂判断，才需要 Python。

例如：

```
def can_open_sealed_shaft(ctx):
    return (
        ctx.flags.rescued_foreman
        and ctx.reputation.scatter >= 3
    )
```

游戏会提供一个只读的 `ctx`，插件只能判断，不能直接改状态。

### 5. 插件私有状态

插件可以保存自己的进度，例如：

```
{
  "rescued_foreman": true,
  "mine_collapse_count": 1
}
```

它只能保存在自己的命名空间里：

```
{
  "plugin_state": {
    "mining_echoes": {
      "rescued_foreman": true,
      "mine_collapse_count": 1
    }
  }
}
```

这样插件之间不会互相覆盖。

## 五、插件运行时，游戏和插件各自负责什么

可以用一张表说明：

| 事情             | 游戏核心负责       | 插件负责         |
| ---------------- | ------------------ | ---------------- |
| 判断事件是否触发 | 执行条件           | 提供条件或规则   |
| 展示 2-4 个选项  | 校验选项数量       | 提供选项数据     |
| 修改玩家数值     | 应用标准效果       | 返回效果描述     |
| 判断死亡和突破   | 核心规则           | 不能直接决定     |
| AI 扩写          | 宿主调用和校验     | 提供基础文本     |
| 插件私有状态     | 存储和版本管理     | 提供状态数据结构 |
| 出错处理         | 禁用插件并继续游戏 | 不处理其他插件   |
| 用户 API Key     | 核心和代理管理     | 不能访问         |

## 六、为什么需要插件契约

如果没有契约，可能出现这些问题：

- 插件直接改核心状态，导致死亡和结局失控。
- 插件 ID 和核心事件冲突。
- 插件改了存档结构，旧存档无法加载。
- 插件抛出异常，整个网站崩溃。
- 不负责核心的组员只能靠猜，无法独立完成扩展。
- 游戏升级后，所有插件一起失效。

契约的目的不是限制作者，而是让插件可以：

- 被自动校验。
- 被单独禁用。
- 被独立测试。
- 在不同版本间迁移。
- 由不负责核心的组员只依靠公开文档完成开发。

## 七、MVP 插件契约至少需要约定什么

后面正式设计时，至少要覆盖这些内容：

1. 插件包的目录结构。
2. `plugin.toml` 有哪些必填字段。
3. 插件 ID 和内容 ID 的命名规则。
4. 地点、事件、选项、结局的数据格式。
5. 每个事件和结果必须提供后备文本。
6. 允许的效果类型，例如数值变化、设置标记、增加物品。
7. 条件函数的输入和返回格式。
8. 插件私有状态的格式和大小限制。
9. 插件版本和接口版本如何兼容。
10. 插件加载失败或运行报错时如何禁用。
11. 插件内容如何写入存档、如何恢复。
12. 哪些行为明确禁止，例如访问 API Key、修改其他插件。

这些内容才是“插件契约”的主体。
