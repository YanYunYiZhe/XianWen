# 《开源软件生态与开发技术》课程大作业任务书

**OSS Portfolio Project：可扩展开源产品工程**

> 默认3人一组，允许使用AI辅助开发。提交一个完整项目，包含源码、设计文档和可运行发行物。

## 一、任务目标

面向明确的目标用户，围绕一个核心使用场景，完成一个有实际使用价值、可运行、可扩展、可验证、可协作、可交付的软件产品。推荐以校园服务插件平台、RAG Connector平台、LLM Provider网关、日志分析插件平台、文件转换插件平台等为载体，实现从用户输入到结果输出的完整业务流程。评价重点是工程实践的完成质量和成员对项目的掌握程度，不以页面、功能、代码量或技术栈数量作为主要依据。完成本文规定的基本要求，提供充分的验证依据，并能清楚解释设计与实现，即可获得满分。CLI、桌面或Web均可，交互方式不影响得分；CLI同样需要可用的输入、处理、输出和错误反馈，不能只有孤立接口或运行不起来的演示片段。

各组自主安排设计、开发、测试和发布。提交截止时间与提交方式另行通知。

## 二、分组与个人责任

- 原则上3人一组，可根据实际人数和成员基础调整为2—4人。各组的基本要求相同，不要求人数较多的小组增加功能。
- 建议三人分别负责核心模块与扩展接口、独立扩展模块、输入输出等配套功能及测试与发布。分工可根据项目实际调整，成员之间应相互配合。每个人都须参与代码开发或测试编写，不能仅负责文档整理。
- 每人至少完成一项有实际内容的代码或测试修改，并通过PR/MR或本地分支审查保留记录；同时至少审查一次其他成员的修改，记录具体意见及处理结果。
- 每人须能够说明自己的贡献，解释一条完整的程序运行流程，并理解至少一个由其他成员负责的接口或模块。
- 独立扩展应由组内不负责核心模块开发的成员完成，不要求组外开发者参与。扩展开发者应根据公开的接口约定和接入说明实现新功能，无需修改核心模块的内部代码。

## 三、最小完成范围

### 1. 一个核心场景

用一句话说明“谁，在什么情况下，用本项目完成什么任务”。实现“用户输入/选择→核心处理与扩展调用→可核对的结果→必要的错误反馈”的完整路径，并能重复演示。核心应有可用的基础能力，接入独立扩展后增加实质能力，可用同一组样例比较接入前后结果。基础能力可内置在核心模块中，无需为此另做一个独立插件。在README中列明本次不实现的功能。

《项目选题与参考案例》提供项目场景、架构示意、三人分工和演示流程。每组选择一个方向，根据基本要求确定实现范围。项目应完整包含核心产品、公开接口约定、独立扩展、有效测试、协作和发布。

默认不要求登录权限、数据库、复杂前端、多服务、云部署、插件市场、热加载或多种扩展机制。确有必要才采用，不能以这些内容替代课程核心要求。

### 2. 一种扩展机制与一个独立扩展

选择插件（Plugin）、服务提供接口（SPI）、数据连接器（Connector）、服务适配器（Provider）、规则扩展等机制，实现一个能够增加实际功能的独立扩展。核心模块与扩展模块应分别组织，职责清晰。双方通过公开的接口约定协作，包括输入输出、调用方式和错误处理规则；扩展不得依赖核心模块的内部实现。

应能说明并验证以下内容：

1. 核心如何注册/发现并调用扩展；
2. 扩展如何独立构建或打包（编译型项目提供独立构建命令）；
3. 按照约定的注册或配置方式接入扩展后，无需修改核心源码即可使用新功能；
4. 禁用扩展或模拟扩展运行失败时，系统的实际处理方式是否与文档说明一致。

允许重启；是否需要重新打包须在README说明。不统一要求Java动态类加载或“Host二进制完全不变”的专项实验。仅多写if/else、更改一个参数，或提供普通CRUD REST接口，不能独立证明扩展能力；基于API的方案也须有独立组件和可运行的新能力。

### 3. 有效测试与基本质量控制

- 核心场景有结果断言，包含正常输入及关键边界或失败输入；扩展至少有一条集成/契约测试，验证接入后的行为。测试应覆盖正常处理、边界情况或失败处理、扩展接入这三类行为；同一用例可以覆盖多类行为，不限定测试框架或用例总数。
- 至少准备一个测试示例：在临时副本中故意引入小错误，确认测试失败；恢复代码后，确认测试通过。无需提交相关日志或截图。
- 提供一条清晰的构建/测试命令；CI默认执行构建与测试，并保留至少一次真实成功记录。
- 风格检查、静态分析、依赖检查中选择一种与项目相关的基础检查即可，不要求同时使用所有工具，也不统一规定测试覆盖率。该项基础检查可在本地运行，不强制额外接入CI。
- 有必要的异常提示和配置说明；不把密码、Token或API Key写入仓库。外部服务不是必需条件；如采用，提供可重复运行的本地样例或Mock路径。

### 4. 真实组内协作

主要改动经过“问题描述→分支→PR/MR→Review→修改或有依据的回应→合并”。问题可在Issue中记录；小改动可直接在PR中说明，不要求为凑数量单独创建Issue。

平台不可用时，可使用本地分支审查：保留Git分支和提交，在README中集中记录作者、实际审查人、被审查的Commit、具体意见、作者处理/回应、更新后的Commit及最终结论。不另交审查表，也不能用AI冒充审查人。

至少有一条Review针对程序行为、边界情况、失败处理、测试或扩展接口提出具体意见，不能只有“LGTM”。新提交后核对相关修改再决定合并。不要求5个Issue、5个PR等统一总量；重点检查审查内容是否具体、修改过程是否有记录可查。

### 5. 一次可追溯发布

版本按实际成熟度选择，如0.1.0，不强制1.0.0。发布前提交代码及版本说明，确认工作区干净，构建/测试通过，再运行实际交付物。为最终提交打版本Tag，推荐附注Tag。

交付物可以是JAR、发行ZIP、可运行目录或适合该项目的其他产物，配运行命令和环境要求；不能依赖开发者的IDE才能运行。Docker按需采用，不是必选项。

仓库外release/RELEASE.md记录最终Commit、Tag目标、制品SHA-256及运行结果，避免为填写最终SHA再次修改已发布仓库。

## 四、AI使用与验证责任

允许AI辅助选题、设计、编码、测试、配置、Review和文档，不因使用AI扣分，也不要求必须使用。

成员必须验证自己采用的关键输出，能够解释代码和测试。README“成员贡献与AI核验”表中，每人简要记录一条关键建议，说明是否采用、如何验证以及验证结论；未使用写“未使用”。不要求独立AI报告、完整对话、提示词截图或固定使用次数。

AI生成的Review必须由实际审查人核对，不能把自动文本冒充他人审查。AI说“正确”“解耦”“已通过CI”均不能单独作为证据。

## 五、不要求的内容

不要求Star、Fork、下载量、真实用户、外部贡献者、跨组开发、跨组部署、跨组反馈或社区运营，也不把这些内容纳入评分或加分。

不要求独立SECURITY.md、CONTRIBUTING.md、CHANGELOG.md、SBOM、AI_USAGE.md、演示视频、在线Demo、单独个人报告或PPT。运行与贡献说明写入README，系统设计写入docs/DESIGN.md，发布信息写入仓库外release/RELEASE.md。

## 六、设计文档

每组提交一份系统设计文档，随工程保存在`project/docs/DESIGN.docx`。建议导出后约8页或以上，篇幅随项目复杂度调整，不按页数评分。先完成需求、架构与接口设计，开发中持续修订，最终内容应与提交版本一致。

文档至少包含需求与范围、总体架构、模块设计、扩展契约、关键流程、数据与配置、测试方案、设计取舍及局限。至少提供一张架构图、一张关键流程图或时序图，并给出一个独立扩展的接入示例。数据库、Web接口等按实际项目描述，未采用的内容无需凑章节。详细要求见05。

## 七、最终提交：一个ZIP

```text
组号_项目名.zip
└─ 组号_项目名/
   ├─ project/               # 完整工程，含.git、源码、测试、CI、README、LICENSE、docs/DESIGN.docx
   └─ release/
      ├─ 交付物             # 已实际验证的发行物或可运行目录
      └─ RELEASE.md         # 最终身份、摘要、命令和已知限制
```

优先在README写可访问的仓库地址（GitHub/Gitee）；确实无法托管时注明“未托管，以ZIP内Git历史及README审查记录为准”。不要求购买托管服务，也不考核项目的关注度。ZIP始终保留Git历史，但真实CI运行仍单独计分。保留必要第三方许可声明。在README简要说明项目许可证选择、关键依赖的许可义务及贡献与合并规则；扩展契约及兼容策略详见设计文档，README保留接入操作和文档链接。贡献与合并规则可以简洁，兼容性限制应明确说明，不要求多版本兼容框架。

排除缓存、IDE目录、秘密和无关大文件；保留运行所需的小样例和依赖声明。压缩整个目录时确认隐藏的.git也在包内，不能用git archive代替。

不另交源码附件、实验报告、截图、日志、个人文档或答辩PPT。提交前自行将ZIP解压到新目录，按README验证；这是本组自检，不是跨组实验，也不另交自检表。
