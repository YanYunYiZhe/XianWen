# 最终交付模板与自检清单

> 提交一个ZIP，包含完整工程、系统设计文档和可运行发行物。设计文档保存在docs/DESIGN.docx，使用说明写入README，发布记录写入仓库外release/RELEASE.md。

## 一、提交结构

```text
组号_项目名.zip
└─ 组号_项目名/
   ├─ project/
   │  ├─ .git/
   │  ├─ README.md
   │  ├─ LICENSE
   │  ├─ docs/
   │  │  └─ DESIGN.docx
   │  ├─ .gitignore
   │  ├─ 源码、独立扩展、测试、小样例
   │  ├─ 依赖声明/锁文件
   │  └─ CI及所选基础检查配置
   └─ release/
      ├─ 已验证交付物
      └─ RELEASE.md
```

交付物选JAR、发行ZIP、可运行目录或其他合适形式；Docker非必需。工程源码可保留原目录名称，不必为改名而破坏构建。不要将缓存、虚拟环境、IDE目录、秘密或无关大文件打包。解释型项目建议交一个发行ZIP，并在本组自检时解压运行，简化摘要记录。

## 二、README模板（写入工程仓库）

```markdown
# 项目名

## 用户、场景与范围
谁使用；输入→核心处理/扩展调用→可核对的输出；基础能力及扩展新增能力；本次明确不做什么。
仓库地址及访问方式；确实无法托管时注明以ZIP内Git为准。
已有起点的来源和本次新增内容（如适用）。

## 快速开始
运行环境与版本；依赖安装/构建命令；样例与预期结果。
每条命令说明执行目录，替换为本项目实测命令，不保留模板占位符。
交付物运行方式参见并列release/RELEASE.md。
外部服务配置及本地样例/Mock路径（如适用），不填写真实秘密。

## 核心与扩展
简述核心与扩展的作用，链接到docs/DESIGN.md中的架构及接口设计。
独立扩展如何构建/打包；如何接入、禁用；是否需重启或重打包。
接入时核心源码保持不变的核验方法。

## 测试与检查
构建/测试命令；正常、边界/失败、扩展测试分别验证什么。
一个可使测试失败的小错误及恢复方法（可现场演示）。
所选基础检查的命令与范围；CI配置位置、真实运行链接/编号或未执行限制。

## 协作与贡献入口
如何报告问题、创建分支、提交PR并Review，谁审查、谁决定合并（几句话即可）。
代表性PR/Review链接或编号：问题、具体意见、处理及复核结果。
平台受限时简记实际作者/审查人、审查SHA、意见、处理/回应、更新SHA和结论。
链接不可访问时简记关键内容和关联Commit，勿虚构平台结果。

## 成员贡献与AI核验
| 姓名/学号 | 本人实质改动及Commit/PR | 审查他人的改动及结果 | 关键决策与AI核验 |
| --- | --- | --- | --- |
| 成员A | | | 一个建议、采用/拒绝、实际验证和结论；未使用写未使用 |
| 成员B | | | |
| 成员C | | | |

## 许可与已知限制
项目许可证及选择理由；关键依赖的许可义务与必要第三方来源/声明；未覆盖的输入、失败或环境限制。
```

最终Commit和交付物的SHA-256记录在仓库外的RELEASE.md中，无需填入README，以免补充记录后又产生新的提交。构建步骤和公开使用说明仍应在打Tag前提交。

## 三、系统设计文档要求

每组维护一份`docs/DESIGN.docx`，与源码一起纳入Git管理。建议导出后约8页或以上，不含封面与目录；不设硬性页数或字数。文档应说明本项目的实际设计，避免大段通用概念、框架介绍或源码粘贴。

### 内容要求

| 内容 | 需要说明的问题 |
| --- | --- |
| 项目概述与需求 | 目标用户、要解决的问题、核心使用场景、输入输出、主要功能与范围边界；给出核心场景的完成条件 |
| 总体架构 | 主要模块、外部依赖、核心与扩展的边界、依赖方向及选择理由；至少一张架构图 |
| 模块设计 | 各模块职责、主要接口或类、输入输出与相互关系；标注对应代码目录，不必逐类罗列 |
| 扩展机制 | 公开接口约定、数据结构、注册/发现、调用、错误处理、兼容策略；给出一个独立扩展的接入示例，说明如何做到核心源码不改 |
| 关键业务流程 | 选一条从入口到结果的完整路径，提供流程图或时序图，解释关键步骤及至少一种失败分支 |
| 数据与配置 | 核心数据结构、文件/消息格式、必要配置及敏感信息的保护方式；采用数据库时补充主要表及关系，未采用则无需设计数据库 |
| 测试与质量方案 | 正常、边界/失败、扩展接入分别验证什么，关键输入和预期结果；说明CI与所选基础检查的作用，并指向实际测试 |
| 设计取舍与局限 | 说明至少两项有实质意义的设计选择及理由、替代方案或代价；区分已实现能力、已知限制和后续计划 |

至少包含一张总体架构图和一张关键流程图或时序图；可使用Mermaid或清晰的图片。接口设计应写出关键方法/协议、输入输出示例与错误约定，不能只有接口名称。

### 推荐目录

```markdown
# 项目名——系统设计文档

## 1. 项目概述与需求
## 2. 总体架构
## 3. 模块设计
## 4. 扩展机制与接口设计
## 5. 关键业务流程
## 6. 数据与配置
## 7. 测试与质量方案
## 8. 设计取舍、局限与后续计划
```

根据项目实际合并或调整章节，核心设计内容应完整。已有项目须交代原有结构与本次改动。文档在开发前形成初稿，随接口、架构及实现变化更新，最终与提交版本一致；尚未实现的设计明确标注为计划。

### 与其他文件的分工

- `README.md`：项目入口，解决如何安装、运行、测试和接入扩展的问题，并链接设计文档。
- `docs/DESIGN.docx`：解释系统如何组织、为什么这样设计、接口与流程如何工作。
- `release/RELEASE.md`：记录本次发布的版本、Commit、Tag、交付物摘要及运行结果。

相同内容通过链接引用即可，无需在三个文件中重复。设计文档纳入现有架构、扩展及文档质量指标评价，重点是准确、清楚、与实现一致，不按排版或篇幅单独加分。

## 四、RELEASE.md模板（仓库外release目录）

```markdown
# 本次版本交付

- 版本及选择理由：
- 最终Commit（完整SHA）：
- Tag及其目标Commit（完整SHA）：
- 工作区状态、构建/测试结果及CI真实状态：
- 交付物名称、环境要求与运行命令：
- 交付物SHA-256；原件/副本一致性：
- 核心场景及扩展操作的实际结果：
- 本次变化、已知限制/未验证范围：
- 发布决定：RELEASE / HOLD及理由：
```

多个运行文件时，可在本文件下列“相对路径＋SHA-256”表；不额外要求长篇报告。SHA-256用于内容一致性核对，不能单独证明来源或质量。

## 五、自检清单（不另交表）

- [ ] docs/DESIGN.docx内容完整，包含架构图与关键流程图/时序图，且与提交代码一致。
- [ ] 一个核心场景可重复运行，一种扩展机制、一个独立扩展真实可用。
- [ ] 扩展依赖公开接口约定，接入时核心源码不变，失败行为符合声明。
- [ ] 正常及关键边界/失败有断言，扩展有集成/契约测试，能展示测试发现故意引入的错误。
- [ ] 构建/测试命令清楚，CI真实状态如实说明，一种基础检查已执行。
- [ ] 每人有实质贡献并审查过他人，代表性Review有具体意见及处理结果。
- [ ] 发布时工作区无未提交改动，Tag指向最终Commit，交付物与发布记录一致，交付副本可运行、摘要可核对。
- [ ] README成员表含个人贡献和AI核验，或注明未使用AI。
- [ ] ZIP含.git、源码、设计文档、测试、依赖声明、LICENSE、小样例和所需配置，不含敏感信息或缓存。
- [ ] 已在新目录解压提交ZIP并按文档自检，不需要跨组测试。

关键构建、运行或版本与交付物的一致性核对未完成时，写HOLD并说明缺口，按实际完成部分评分。
