# XianWen 五人组分工说明

- 更新时间：2026-11-10
- 适用项目：XianWen 课程 MVP
- 分组情况：5 人组

## 1. 工作简要介绍

XianWen 是一款浏览器端修仙文字游戏。课程 MVP 范围为 10 回合、2 个结局、2 条世界线、1 个主模型预设和 1 个组内独立扩展。

五人分别负责：

- **A：核心规则**
- **B：插件平台与公开契约**
- **C：独立扩展**
- **D：Web 页面与本地存档**
- **E：AI 接入、测试与发布**

分工原则：

1. 每人都要有实际代码或测试贡献。
2. 每人至少审查一次他人的修改，并留下具体意见和处理结果。
3. 每人能解释一条完整运行流程，并理解至少一个他人负责的接口或模块。
4. C 不参与核心模块开发，只能通过公开契约实现独立扩展。

## 2. A：核心规则负责人

 决定玩家做出选择后，游戏里实际发生什么。

### 主要任务与代码

- 定义游戏状态：年份、境界、修为、寿元、伤势、声望、地点、标记和结局。
- 编写新游戏初始化、事件筛选、选项效果应用和回合推进代码。
- 判断死亡、突破、世界线变化和结局。
- 编写至少 3 个基础事件，保证未接入插件时也可游玩。
- 目标代码目录：`src/xianwen/core/`。

### 交付内容

- 核心规则模块。
- 基础事件数据。
- 核心接口说明：输入状态、事件 ID、选项 ID，输出新状态和结果。
- 正常选择、非法选项、回合推进和结局判定的测试。

### 能解释的完整流程

> 新游戏 → 得到候选事件 → 玩家选择 → 核心应用状态变化 → 保存状态 → 进入下一回合或结局。

### 要理解的他人模块

- B 定义的“插件标准效果”如何被核心代码应用。
- D 如何把核心结果显示到页面并保存。

### 主要审查谁

- 主要审查 B 的插件平台，确认插件不能绕过核心规则直接修改状态。

---

## 3. B：插件平台负责人

规定插件长什么样，并保证坏插件不会拖垮游戏。

### 主要任务与代码

- 定义插件目录、`plugin.toml` 字段和内容文件格式。
- 编写插件扫描、加载、校验和注册代码。
- 检查插件 ID、事件 ID、选项 ID、版本和后备文本。
- 捕获插件异常，只禁用出错插件。
- 管理插件私有状态和版本。
- 编写插件作者接入说明。
- 目标代码目录：`src/xianwen/plugins/`。

### 交付内容

- 插件加载器和校验器。
- 公开插件契约。
- 插件作者说明和最小格式示例。
- 正常加载、错误清单、重复 ID、插件异常和禁用恢复的测试。

### 能解释的完整流程

> 启用插件 → 校验并注册插件内容 → 插件事件进入候选池 → 玩家选择 → 插件提交标准效果 → 核心应用或拒绝。

### 要理解的他人模块

- A 的状态迁移和标准效果应用逻辑。

### 主要审查谁

- 主要审查 A 的核心接口，确认核心与插件边界清楚。
- 审查 C 的扩展，确认扩展只使用公开契约且未修改核心代码。

---

## 4. C：独立扩展负责人

按照公开说明书制作第一个独立扩展，不修改游戏核心。

### 主要任务与代码

- 只依据 B 的插件契约和接入说明开发扩展。
- 新增 1 个地点。
- 新增 2 个事件。
- 新增 1 个条件或行动。
- 新增 1 个结局变化。
- 为每个事件和结果提供后备文本。
- 编写必要的扩展规则代码和扩展测试。
- 目标代码目录：`plugins/<plugin-id>/`。
- 不修改 `src/xianwen/core/` 内部代码。

### 交付内容

- 一个可独立启用和禁用的扩展包。
- 扩展契约测试和存档恢复测试。
- 启用插件前后的对比演示。
- 对插件文档实际可用性的反馈。

### 能解释的完整流程

> 启用扩展 → 新地点和新事件出现 → 玩家触发扩展事件 → 扩展提交标准效果 → 核心应用效果 → 保存并重新加载后扩展状态仍存在。

### 要理解的他人模块

- B 的插件加载、校验和错误处理流程。
- A 如何应用标准效果并决定最终状态。

### 主要审查谁

- 主要审查 B 的公开契约和接入说明是否足以让非核心成员独立开发。

---

## 5. D：Web 与存档负责人

让玩家能看见游戏、点击选项、保存进度并刷新后继续。

### 主要任务与代码

- 实现开始页、游戏页和结局页。
- 使用 HTMX 提交玩家选择并更新页面。
- 显示状态变化、结算、错误提示和 AI 后备提示。
- 使用 `localStorage` 保存和恢复当前局。
- 确保 API Key 只存在页面内存，不进入存档。
- 目标代码目录：`src/xianwen/web/`、`templates/`、`static/` 和存储适配代码。

### 交付内容

- 可操作的浏览器页面。
- 浏览器与 FastAPI 的请求格式说明。
- 本地存档实现。
- 新游戏、选择、刷新恢复、损坏存档和 Key 安全的测试。

### 能解释的完整流程

> 玩家点击选项 → 页面发送请求 → 核心规则处理 → 页面显示结算 → 写入 localStorage → 刷新后恢复当前局。

### 要理解的他人模块

- A 的核心输入输出接口。
- E 的 AI 失败和后备处理接口。

### 主要审查谁

- 主要审查 E 的 AI 后备、错误反馈和与页面相关的质量检查。

---

## 6. E：AI、测试与发布负责人

接入一个主模型，准备无 Key 的后备路径，并完成自动检查和发行。

### 主要任务与代码

- 实测并选择一个主模型预设。
- 编写模型请求、响应解析和 AI 输出校验代码。
- 实现超时、重试、调用预算和后备模式。
- 编写本地 Mock，保证测试不依赖真实模型服务。
- 配置 GitHub Actions，运行 ruff、mypy、pytest 和 `uv build`。
- 完成 Tag、发行 ZIP 和 `release/RELEASE.md` 验证。
- 目标代码目录：`src/xianwen/ai/`、`.github/workflows/` 和 `release/`。

### 交付内容

- 一个主模型适配器。
- 本地 Mock 和无 Key 的完整可玩路径。
- AI 非法响应、超时、后备和 Key 脱敏测试。
- CI 工作流、真实成功记录和可解压运行的发行物。

### 能解释的完整流程

> 页面请求场景 → AI 层读取候选事件 → 主模型扩写或使用后备文本 → 校验 AI 输出 → 页面展示 → 玩家选择 → 核心应用结果。

### 要理解的他人模块

- D 的页面请求和存档流程。
- B 的插件事件如何进入候选池。

### 主要审查谁

- 主要审查 D 的页面调用、错误反馈和 Key 处理。

## 8. Review 闭环

### Review 配对

| 作者 | 主要审查人 | 审查重点 |
| --- | --- | --- |
| A：核心规则 | B | 状态迁移、边界条件、插件标准效果是否可接入 |
| B：插件平台与契约 | A、C | A 检查核心边界；C 检查契约和文档是否可用 |
| C：独立扩展 | B | 是否只使用公开契约、是否修改核心、失败和存档是否正确 |
| D：Web 与存档 | E | 请求校验、错误反馈、Key 安全和存档恢复 |
| E：AI、测试与发布 | D | AI 后备、页面反馈、构建和发行物可运行性 |

### 闭环关系

- A 和 B 互相审查核心与插件边界。
- B 和 C 互相审查插件契约与独立扩展。
- D 和 E 互相审查页面、AI 后备、测试与发行。
- 每个人都至少审查一次他人修改，每项主要改动至少有一名他人审查。

### Review 记录要求

1. 每个主要改动使用独立分支和 PR/MR；平台不可用时保留本地分支审查记录。
2. Review 意见要指出具体问题，例如行为、边界、失败处理、测试或接口问题。
3. 作者需要回应、修改或说明不修改的理由。
4. 更新代码后，审查人需要复核相关修改再同意合并。
5. 不能只写 LGTM，也不能由 AI 冒充实际审查人。

## 9. 执行底线

- 每人至少完成一项有实际内容的代码或测试修改。
- 每人至少审查一次其他成员的具体修改。
- 每人能独立讲解本表中的一条完整流程。
- 每人能解释至少一个他人负责的模块或接口。
- C 的扩展 PR 不得修改核心模块内部代码；契约不足时由 B 修改插件平台。
- README 中记录每位成员的代表性 Commit/PR、Review 和处理结果，以及一条 AI 核验记录。
